# ADR 0001: Sandboxed document worker

Status: accepted
Date: 2026-09-16
Decides: the four open decisions from #78/#81 (worker process model, document handoff, Linux sandbox layer, PDFium retention)
Contracts this builds on: `sidecar/src/limits.rs` (#83), `electron/main/protocolSources.ts` + `electron/shared/pathSchema.ts` (#84), `frontend/src/lib/epub/contentPolicy.ts` (#82)
Implementation plan: `docs/superpowers/plans/2026-09-16-issue-81-worker.md`

## Context

Every imported or opened EPUB and PDF is hostile input, and today the long-lived sidecar parses it inside the process that owns SQLite, the library filesystem, and path authority (`docs/ARCHITECTURE.md`). A single parser vulnerability (the lopdf stack-overflow class, ZIP bombs, PDFium memory corruption) reaches the user's whole library. Task 1 (#83) added a quota table with typed errors and documented two stages that still run to completion once started: lopdf's `Document::load` and the PDFium cover render (`docs/RESOURCE_LIMITS.md`). Task 2 (#84) centralized path authority (book id to database lookup to stored path, T-1). Task 3 (#82) fenced EPUB content in the renderer. Quotas cap what a hostile file can burn; they do not reduce what a parser compromise can touch. That is a privilege problem, so the parser moves into a process that holds strictly less authority than the sidecar.

Scope note: the raw byte paths (`load_book_file`, `load_book_file_range`, cover-file reads) are plain reads of files the sidecar itself resolved through the database. They parse nothing, so W-1 does not implicate them and they stay in the sidecar. Everything that decompresses, parses XML, walks PDF objects, or rasterizes moves.

## Decisions

### D1. One short-lived worker process per job, spawned by the sidecar

The worker is a separate Rust binary, `tuxbooks-worker`, and the sidecar spawns it fresh for every parse job: one document, one operation, one bounded response, then the process exits. "Job" means one request, not one document lifetime; a resource read, a session build, a metadata parse, and a cover render are each their own process.

Why per job rather than one long-lived worker:

- A long-lived worker that misbehaves on document N must be killed, which drops every queued job and requires a supervisor with a restart ladder, health checks, and pending-request rejection. That is a second copy of the `Sidecar` supervision machinery in `electron/main/sidecar.ts`, built around a process whose only property we care about is that it dies on demand. Per-job spawning makes restart the next spawn and containment automatic: a compromised or corrupted worker never serves a second document.
- Long-lived workers accumulate state across hostile inputs: PDFium's process-global bindings (`RENDER_LOCK` and `OnceLock` in `sidecar/src/pdf/render.rs` exist precisely because of this), allocator fragmentation, cached parser state. Per-job processes start clean.
- W-8's run-to-completion gap closes only with a kill. `Document::load` and the PDFium render cannot be interrupted in-process, which is why `docs/RESOURCE_LIMITS.md` calls them a documented gap. The sidecar kills the worker at the wall-clock deadline, mid-stage if needed. A long-lived worker would impose the same kill semantics on unrelated queued jobs.

The cost is a fork and exec per job, a few milliseconds, plus parser start-up. Against a 30 second parse budget and background imports this is noise. On the EPUB reading path every member read pays it (see Consequences for the measurement plan). The sidecar, not Electron main, spawns the worker: the sidecar already owns path authority (T-1 resolves book id to path in the database), so the handoff needs no new authority holder, Electron main stays plumbing, and the worker boundary never crosses into TypeScript.

The worker keeps the JSON-RPC-over-stdio pattern in shape only: it reads one newline-delimited JSON request from stdin, writes one JSON response to stdout, and exits. The exit contract matters: the worker exits 0 whenever it wrote a well-formed response, whether that response reports success or a typed failure, and nonzero only when no well-formed response exists. That is what keeps parse, limit, and sandbox failures typed at the sidecar instead of collapsing into crash reports, and it is what makes a CPU-rlimit kill (no response, SIGXCPU) distinguishable from a parse rejection (a `Failed` response). No method table, no ids, no events. A long-lived protocol would buy nothing here.

### D2. The document crosses as one pre-opened file descriptor

The sidecar resolves the path (book id to database to stored file, or a scan result), opens the file read-only, and passes the file descriptor to the worker as fd 3. The worker never receives a path, never calls `open()`, and cannot name a file. This is the "opaque handle" option W-5 explicitly allows.

- It composes with the OS sandbox. The worker needs zero filesystem access, so the Linux layer (D3) can deny every filesystem operation outright. A path allowlist would instead require the worker to enforce its own confinement, which a compromised worker ignores; and Landlock rules would have to be re-armed per job around changing paths.
- It matches Task 2's trust split: path authority stays in the sidecar; the worker inherits none of it.
- It preserves streaming. ZIP parsing needs a seekable stream; the fd is seekable, so EPUB parsing streams from disk under the quota table instead of buffering a 1 GiB source in memory. (PDF ops buffer the fd into a bounded byte slice because lopdf and PDFium accept memory inputs; that is capped by `max_source_file_bytes` and `RLIMIT_AS`.)
- The worker's stdout/stderr/stdin are its only other descriptors. The spawner's `pre_exec` hook calls `close_range(4, u32::MAX)` before `dup2(fd, 3)`, so on Linux the child holds exactly fds 0, 1, 2, 3 by kernel enforcement rather than by discipline (W-7). On other unixes, where `close_range` is not available, the fallback is std's close-on-exec discipline plus the spawner's own descriptors; that is a documented gap there, not an invariant.

The mechanism is `dup2` onto fd 3 in a `pre_exec` hook (POSIX; async-signal-safe) and `File::from_raw_fd(3)` in the worker, which first verifies with `fcntl` that fd 3 exists and with `fstat` that it is a regular file. Windows has no equivalent for arbitrary inherited handles in Rust's std, and no Windows target is shipped (`electron-builder.yml` builds deb, rpm, AppImage only). When Windows packaging happens, its worker build should take the document as in-memory bytes on stdin; this is recorded as a follow-up, not designed here.

### D3. Linux hardening: Landlock plus a seccomp deny-list plus rlimits, applied by the worker itself

Three small, dependency-free mechanisms, applied by the worker at startup in a fixed order, all usable headless in CI without root:

1. `PR_SET_PDEATHSIG` first (W-11): lifecycle containment only, mirroring `sidecar/src/main.rs`. A compromised worker can clear it, so it is never counted as a boundary.
2. PDFium probe and load, when the job needs it: `dlopen` opens files, so it must happen before filesystem lockdown. No other stage opens files.
3. Landlock (kernel 5.13+, 2021): a ruleset over filesystem access classes only, carrying zero rules, so every filesystem access is denied. The ruleset attribute is the fs-only struct the ABI has had since 5.13, so no attr-size negotiation is needed and no kernel in the supported floor can reject it. If `landlock_restrict_self` cannot be applied, the worker fails the job with a typed `sandbox` error and parses nothing. Fail closed, as required. Every distro this project packages for ships 5.15 or newer; kernels older than 5.13 get a clear typed error, not silent parsing. Landlock's network ABI is deliberately not used (see the rejection below).
4. seccomp classic-BPF deny-list (`SECCOMP_SET_MODE_FILTER` after `PR_SET_NO_NEW_PRIVS`): denies process creation (`execve`, `execveat`, `fork`, `vfork`), namespace creation and introspection (`clone` with namespace flags, `unshare`, `setns`, `mount`, `umount2`), debugging (`ptrace`, `bpf`, `keyctl`, `kexec_load`), and socket creation outright (`socket`, `socketpair`, `connect`, `bind`, `listen`, `accept`, `accept4`, `sendto`, `recvfrom`). Denying `socket` is what owns W-3: one rule closes TCP, UDP, AF_UNIX, and netlink creation for every address family, which is stronger and simpler than Landlock's network ABI (TCP bind/connect only, kernel 6.7+). A deny-list, not an allow-list: allow-lists track libc and Chromium maintenance schedules, and this worker's legitimate syscall set is small and stable.
5. rlimits: `RLIMIT_CPU` at the job's `max_parse_seconds` (kernel CPU backstop beside the sidecar's wall-clock kill) and `RLIMIT_AS` at a documented 3 GiB cap (headroom over the 2 GiB total-uncompressed quota). Memory and CPU are therefore kernel-enforced inside the worker, per job, which is exactly the accounting `docs/RESOURCE_LIMITS.md` deferred to #81.

Self-verification closes the loop (W-10 without trust-me): after applying the layers, the worker attempts to open `/proc/self/status` and to create an INET socket, expects both to fail, and refuses the job if either succeeds. The same probes are the CI hook: a `selftest` job type returns the per-layer status so tests can assert enforcement, and the Landlock test applies a ruleset in-process (thread-scoped) while the seccomp test forks, because a seccomp filter is process-wide and irreversible.

Rejected:

- bubblewrap: an external binary the app cannot assume on user systems, a packaging liability for AppImage, and CI friction for no added strength over in-process Landlock plus seccomp here.
- systemd sandboxing: needs a service unit and a systemd user session the app does not control; not portable across launch paths or CI.
- seccomp alone: denying `open*` post-start is brittle (glibc and Rust backtraces touch `/proc` lazily) and a failed parse from a syscall surprise is a worse failure mode than Landlock's explicit path-based rules.
- The `landlock` and `libseccomp` crates: their convenience is real, but the first defaults to best-effort degradation (silently weaker sandboxing, the one failure mode this design must never have) and the second adds a shared-library dependency to the trust boundary. The hand-rolled FFI is about 150 lines, fully auditable, and its effect is proven by self-verification rather than by trusting the wrapper.
- Landlock's network ABI (TCP bind/connect handling, kernel 6.7+): it covers TCP only and leaves UDP, AF_UNIX, and netlink sockets open, so it cannot own W-3 by itself; using it would also mean carrying two ruleset-attribute layouts (the pre-6.7 fs-only struct and the 6.7+ struct with `handled_access_net`), and the bigger attribute is rejected with `E2BIG` by every kernel in the 5.13-6.6 range. seccomp's `socket` denial covers every address family in one rule on every supported kernel, so the Landlock network machinery is redundant. Dropped as YAGNI.

### D4. PDFium stays for covers and moves into the worker

`docs/BUILD.md` already settled the engine question: renderer MuPDF rasterizes whole documents for the reader and cannot replace import-time, no-UI, single-page covers. PDFium remains the import-time cover engine.

The placement question is decided by P-1 and by evidence: PDFium is a C library parsing hostile PDFs, and `sidecar/src/pdf/render.rs` documents a SIGSEGV from concurrent renders. A PDFium crash inside the sidecar is a W-9 violation today. In a per-job worker it becomes the cheapest possible containment story: the crash kills one job, the sidecar reports a typed error, the next spawn is clean. The render also moves out of the run-to-completion gap, since the sidecar can kill the worker mid-render at the deadline. `libpdfium.so` is `dlopen`ed before the Landlock lockdown (D3 ordering); the candidate directories travel in the job payload, not the environment (W-7).

### D5. Same crate, second binary, parse modules become worker-internal

`tuxbooks-worker` is a second `[[bin]]` in the `sidecar/` crate, linking the existing `tuxbooks_lib`. The EPUB/PDF parse modules stay where they are; their entry points gain reader-based variants and the sidecar's services stop calling them directly, routing through a small worker client instead. A separate parse-only crate was rejected: it would fork the parser code into two copies that can drift, and drift between the parser the sidecar shipped and the parser the worker runs is a supply-chain defect. The cost of the single-crate choice is that the worker binary links the database code it never runs; its entry point wires only the parse path, and on Linux Landlock makes every database file unreachable at the OS level regardless (W-2).

Failure modes are fail-closed throughout: if the worker binary is missing, the sidecar returns a typed `worker-unavailable` error and parses nothing; it never falls back to in-process parsing, because a packaging bug would otherwise silently reopen the privilege hole.

## Consequences

- Every EPUB resource request now pays one fork and exec. `docs/PERFORMANCE.md` PERF-13 gets a note, and `just bench-reader` measures the reader paths before and after the flip. If the cost ever shows up, the follow-up is a session-scoped worker (one process per opened book, killed on close), which preserves the containment property (bounded lifetime, one document) without a design change.
- PDF ops buffer the source (up to 1 GiB) once inside the worker, on top of the sidecar's transient read. Bounded by quotas and `RLIMIT_AS`; real books are megabytes.
- Embed jobs cap the source document at 512 MiB (`max_embed_source_bytes`, a typed limit error): an embed's peak is roughly source plus rewritten document plus base64 output (x4/3), and a specific bounded-resource error beats an allocator abort that the sidecar would only see as a crash.
- Windows handoff (in-memory bytes on stdin) is a follow-up when a Windows target ships.
- The worker binary links the full crate. Accepted for the single parser copy (D5); the entry point is the review surface.
- Import concurrency stays at the sidecar's 3-permit semaphore; workers are cheap and independent.
- `docs/ARCHITECTURE.md` gains the worker process model, `docs/RESOURCE_LIMITS.md` retires the run-to-completion gap note, `docs/BUILD.md` and `docs/RELEASE.md` gain the worker packaging entry, and `docs/TESTING.md` gains the sandbox test layer notes.
- The Task 2 ledger items are honored here: the sidecar's JSON-RPC layer maps worker outcomes to typed error codes (deadline, limit, sandbox, worker failure) so `electron/main/protocolSources.ts` can stop treating every `RpcFailure` as 404 when a later task touches protocol error mapping; the 2 GiB response-line cap carries over to the worker channel and stays above the 1 GiB source quota.

## Risks accepted

- A seccomp deny-list can break a future parser that legitimately needs a denied syscall. The failure is a typed error, loud and testable, never silence. An allow-list was rejected as unownable at this project's scale. Denying `socket` outright is broader than the worker needs (it needs no sockets at all) and is what closes UDP, AF_UNIX, and netlink in one rule.
- Kernels older than 5.13 cannot parse documents at all under this design. Accepted: fail closed beats silently unsandboxed parsing, and affected systems predate every supported distro target.
- The hand-rolled sandbox FFI carries implementation risk that a wrapper crate would hide. Self-verification at startup (deny probes must fail, or the job fails) bounds that risk by construction.
- If a hostile document compromises the worker, it holds one read-only fd, no network, no filesystem, no spawn authority, and a deadline. That is the designed worst case, and it is the point of this ADR.
